# 追剧系统 100+ 订阅规模扩容设计

> 状态：已实现（914 测试全绿，web-ui build 过）。实现时修正两点：①排播对齐（播出前休眠 +15min、播后短轮窗口）在 `scheduleNext` 中本已存在，P1 实际增量仅为"完结看完轻查 24h→7 天"；②jitter 未做——到期任务按 nextCheckTime 升序排队 + tryLock 防重，整点踩踏无害，且随机量会击穿现有精确断言。P2 落地为 maxChecksPerRound 10→30、checkConcurrency 3→4（到期升序取任务 + 每小时 sweep + tryLock 本就构成预算制，无需额外时间窗逻辑）。
> 基线：feat/media-subscription 分支。
> 关联文档：`docs/media-subscription-design.md`（主设计，顶部有历轮优化补记）。

## 1. 背景与问题

当前实现按个位数到几十个订阅的假设调参。订阅量到 100+ 后，瓶颈不在数据量（几百订阅 × 每个几十条集源行，H2/MySQL 与现有索引都毫无压力），而在**巡检吞吐**与**外部搜索源预算**；前端列表/事件流的全量展示也会先于后端变得难用。

### 1.1 现状盘点

| 组件 | 现状 | 位置 |
|---|---|---|
| 到期扫描 | `sweep()` 每小时 :20 跑一次，每轮 ACTIVE/ENDED 各取 `maxChecksPerRound=10` 条 | `MediaSubscriptionCheckService.sweepDue()` |
| 巡检并发 | `checkConcurrency=3` 线程池（msub-check-N） | 构造器 |
| 搜索并发 | 固定 5 线程池，五路搜索共享 | `searchExecutor` |
| 检查间隔 | 统一 `checkIntervalHours=6` | `AppProperties.Subscription` |
| 元数据短轮 | :35 对 RETURNING 状态每小时刷一次（airingRefreshHours 节奏） | `refreshAiring()` |
| ENDED 短路 | 轻查短路 + watchingRecently 每日完整巡检放行 | 已实现 |
| 前端列表 | 订阅列表全量拉取，事件流不折叠 | web-ui |

### 1.2 吞吐账

每小时最多消化 10 个 ACTIVE 完整巡检，6 小时间隔下稳态上限约 **60 个在播订阅**。到 100+ 后 `nextCheckTime` 开始积压、越拖越晚，用户感知为"更新滞后半天到一天"。

同时每次完整 doCheck 是五路搜索 + 挂载 + 列目录 + 流探测，打的都是外部站点（玩偶聚合 11 站、TG、pan-site 系列）。目前没有证据表明这些站点会限流（既有并发下未见限流特征），但并发提上去后外部行为未知，作为防御性考虑保留可选的站点级限流（见 3.3），不作为本设计的依据。

## 2. 设计原则

- 纯增量：不动 doCheck 主流程，不动已修好的删除竞态/ENDED 短路/换季重置链路。
- 分层优先于扩容：100+ 订阅里真正"热"的通常只有十几部在播剧，把冷订阅的检查预算省下来，比加并发更有效。
- 搜索开销与订阅总数解耦：现状搜索只在资源失效/有更新时触发，本设计不预设站点会限流。

## 3. 方案

### 3.1 分层检查节奏（核心，收益最大）

废弃"一个 checkInterval 包打天下"，按订阅状态分层：

| 层 | 条件 | 节奏 |
|---|---|---|
| 热：在播有更新 | ACTIVE 且近期检出新集 | 维持 6–12h 短轮 |
| 在播、日程已知 | 下集播出时间非空 | `nextCheckTime` 对齐到**下集播出后 1–2h**，非固定间隔 |
| 完结未看完 | ENDED 且 watchingRecently | 每日轻查放行（已有，维持） |
| 完结看完 | ENDED 且近 7 天无播放 | 轻查拉长到每周（官方加重重开场景，一天一次纯属浪费） |
| 未开播 | 播出时间在未来 | 播出前休眠（已有，确认规模化后仍生效） |

排播对齐的关键：PlayScheduleBridge 已经写入官方排播时刻，doCheck 尾部排 `nextCheckTime` 时优先用"下集播出时间 + 1~2h"，无排播数据再回落现有固定间隔。周更剧从每天查 4 次降到每周查 1 次，搜索预算省 90%+。

实现要点：
- 排期逻辑收敛到 doCheck 尾部现有的 nextCheckTime 计算处，单点修改。
- 对齐时间加 ±30min 随机 jitter，避免同档期多部剧同时到期踩踏。
- 新订阅创建/批量导入（片单追更一次 20 部）时对首查时间也加 jitter。

### 3.2 sweep 预算制（替代固定条数）

`maxChecksPerRound=10` 是硬上限，积压时无自愈。改为时间预算制：

- sweep 启动时计算本轮时间窗（建议 50 分钟，留 10 分钟余量给 :30 分享校验）。
- 按 `nextCheckTime` 升序取任务提交，池满即止，未取到的下小时继续——到期早的天然优先，积压时自动降级为"最老的先查"，不丢任务。
- `maxChecksPerRound` 保留为安全上限（建议默认提到 30），防止时间预算内提交过多小任务。
- `checkConcurrency` 默认提到 4，保持可配；搜索池维持现状 5 线程（若日后观测到外部站点异常再考虑限流，见 3.3）。

### 3.3 搜索开销盘点（现状已达标，无新增项）

五路搜索本来就只在**有信号时触发**，不存在"每轮巡检无条件搜索"：

- `fillPool()` 池内有 ≥1 可用候选直接 return——只有资源失效退役把池耗光（`exhausted` 路径）或强制刷新才搜索；
- 缺集补搜 `fillGaps()` 只对官方已播但本地缺失的集发起，且有播出窗口判定与补搜冷却节制。

因此 100+ 规模下**每轮巡检的真实开销在列目录/流探测/挂载维护，不在搜索**；搜索压力只随"实际失效/实际更新"的事件数增长，天然与订阅总数解耦。本设计不需要额外的搜索去重。

**站点级限流（可选，防御性）**：目前没有证据表明站点搜索会被限流，不作为本设计的必要项。仅当并发提高后观测到搜索失败率上升/结果异常衰减时，再在五路搜索汇聚处按站点加信号量或最小间隔，独立于 checkConcurrency。

### 3.4 数据与事件

- `msub_event` 加保留期清理：每订阅保留最近 200 条或全局保留 90 天（取先到者）。挂在 sweep 尾部 `retryErrors()` 附近顺手执行，每日一次即可。
- 实体量级不需要任何 schema 变更，现有索引够用。
- 挂载数量：100+ 常驻挂载对内嵌 AList 无实质压力，盘线路 `1@{pid}` 机制不受影响，不改。

### 3.5 前端列表

- 订阅列表页加状态筛选（在播/完结/异常/全部）+ 分页（或虚拟滚动），避免 100+ 条全量渲染。
- 事件流按订阅折叠或分页。
- 批量操作：沿用"每组独立全选/全不选/反选"的既有约定，不设全局批量。

## 4. 落地顺序

| 顺序 | 内容 | 理由 |
|---|---|---|
| P1 | 3.1 分层节奏 | 核心收益，先把冷订阅的检查预算省下来 || P2 | 3.2 预算制 sweep + 并发/上限调参 | 吞吐自愈 |
| P3 | 3.5 前端分页筛选 | 用户最先撞到的墙，工作量最小 |
| P4 | 3.4 事件清理 | 随手带 |

## 5. 风险与边界

- **排播对齐依赖排播数据质量**：无排播数据的剧回落固定间隔，行为与现状一致；排播时刻错误的剧（平台临时改档）最坏延迟到下一个固定间隔，由短轮元数据刷新纠正。
- **元数据未变不搜索的漏检窗口**：官方集数没变但资源悄悄失效的场景，由播放失败标记（markPlaybackFailure → 越过短路）和资源池健康条件兜底——池不健康就不满足跳过条件，照常搜索。
- **多实例**：与既有口径一致，本设计仍按单实例假设（取消标记/限流器均为内存态）。
- **不打扰已修复链路**：删除竞态八道 stopIfDeleted、ENDED 短路/重开、换季重置均不受影响——预算制只改"取哪些任务"，任务体仍是同一个 check()。
